# 工作台目标版本：在线事件数据融合改造实施方案 V1

> 文档性质：实施前设计与审计结论，不代表已完成开发。  
> 适用范围：最强题材、涨停分布、涨停简图、情绪速览、人气热榜、板块精选、首页渐进式研究视图。  
> 明确前提：本项目允许联网。通达信本地数据是可复核的研究基础，不是唯一数据源，也不构成在线数据禁令。  
> 本轮边界：只形成方案，不修改业务代码、数据库或页面。

## 1. 结论与方向

M7–M15 已经搭建了历史快照、板块周期、主线、五类结构、联动、市场周期和在线热榜等底层能力，但最终页面偏向“把已计算字段展示出来”，没有围绕每天真正需要回答的问题组织功能；同时，涨停事件、炸板、题材分组等已有公开事件数据仍被本地日线重建替代，导致口径误差、未知值过多和计算量过大。

目标版本改为双引擎：

1. **在线事件引擎**：负责当日涨停、炸板、跌停、强势题材、事件时间、人气榜、公开题材说明等现成事实。
2. **本地研究引擎**：负责 MA、RPS、创新高、成交额变化、板块连续性、成员留存、五类结构和可追溯历史。
3. **融合层**：按证券代码和板块映射把两类证据并列组合，不把推断写成事实，不把平台热度写成行情强度。
4. **页面层**：首页按“市场概况 → 强势题材 → 板块梯队 → 代表个股”渐进展开，详情功能放入少量二级页，不再把大量全市场明细一次性送入浏览器。

该方案不是在原 M7–M15 页面上继续堆字段。它保留已经正确的快照、合同和本地因子基础，重做用户可见的信息架构、在线事件域和融合逻辑。原 M7–M15 文档只能作为底层参考，不能直接作为目标版本的页面实施清单。

### 2.2 当前项目代码与页面能力

现有后端已经有 `/api/dashboard`、`/api/sectors/cycle`、`/api/mainlines`、`/api/market/cycle`、`/api/limit-ladder`、`/api/stocks/technical`、`/api/stocks/new-highs`、`/api/queues`、`/api/linkage`、`/api/hot-rankings` 等接口。它们可作为本地增强来源，但存在以下产品层问题：

1. 首页缺少清晰的研究顺序，市场、板块、股票能力分散。
2. 当前涨跌停和梯队过度依赖本地参考价规则；参考状态未知时，市场周期的涨跌停大量缺失。
3. 人气热榜当前只真正覆盖部分榜单，页面没有把 1 小时、24 小时、飙升、板块热度组织成可切换研究工具。
4. 在线数据与本地字段虽然技术上分离，但页面没有形成“在线事实 + 本地增强”的统一阅读体验。
5. 板块精选、主线、板块周期和联动功能之间存在重复入口，用户仍需自己拼接结论。

### 2.3 当前数据库膨胀事实

当前主库约 1.6 GiB，仅在 `analysis_snapshot_entries` 中覆盖 5 个交易日，却已有 47 个 `SUCCESS` 分析快照。主要明细量：

| 表 | 行数 | 不同切片数 | 交易日数 |
|---|---:|---:|---:|
| `sector_member_state_daily` | 3,365,740 | 31 | 5 |
| `stock_high_daily` | 1,112,040 | 31 | 5 |
| `stock_sector_associations_daily` | 671,568 | 9 | 4 |
| `historical_structure_daily` | 409,510 | 15 | 3 |
| `stock_strength_daily` | 278,009 | 31 | 5 |
| `stock_technical_daily` | 278,009 | 31 | 5 |
| `limit_ladder_daily` | 129,717 | 21 | 3 |
| `market_reference_daily` | 111,204 | 18 | 3 |

根因不是“A 股一天本来就有这么多必要结果”，而是多个成功快照保留了重复或近似的全市场切片，并且多个功能把所有股票、所有板块成员、所有窗口都按日物化。目标版本实施期间必须遵守一个临时止损原则：**新增在线功能不得再创建全市场日明细；事件域只保存发生事件的股票和题材，热榜保持请求级不落盘。** 全面存储治理另开独立审计项，不在本轮偷偷删除历史数据。

## 3. 目标信息架构与页面布局

主导航控制为五项，复杂度由二级页吸收：

| 主导航 | 二级功能 | 首要问题 |
|---|---|---|
| 首页 | 市场概况、强势题材、板块梯队、代表个股 | 今天市场怎么样，先看什么 |
| 情绪与涨停 | 情绪速览、涨停简图、涨停分布 | 事件强度、梯队和题材聚集在哪里 |
| 板块研究 | 板块精选、周期矩阵、主线跟踪、属性库 | 哪些板块值得继续研究，为什么 |
| 个股研究 | 优先研究、五类结构、创新高/RPS、板块联动 | 哪些股票值得研究，强势来源是什么 |
| 热度观察 | 人气热榜、飙升榜、热门概念/行业 | 平台关注度在变化什么 |

### 3.1 首页

首屏只请求一份紧凑摘要，不加载全市场股票列表：

1. 市场概况卡：上涨/下跌/平盘、涨停/炸板/跌停、封板率、全市场成交额、更新时间和来源状态。
2. 强势题材：前 6 个题材，每项显示涨停数、最高板、强势股数、代表股、在线说明和本地连续性。
3. 板块梯队：新晋、持续、再加速、高位收缩四组，每组最多 5 个；来自本地主线与在线事件融合。
4. 代表个股：按板块分组，每板块最多 3 只；展示价格、涨幅、成交额、板位、RPS20、MA 状态和五类结构标签。

点击任何卡片才请求对应详情。首页首屏 DTO 目标不超过 200 KiB、DOM 节点不超过 500、首次可交互不超过 1.5 秒（本地服务、正常磁盘）。

### 3.2 情绪与涨停页

- 顶部固定 6 张统计卡，不做横向超宽表。
- 二级标签切换时才请求对应接口；切换后取消前一请求。
- 涨停简图采用“板位折叠组 + 虚拟化表格”，默认展开最高板、二板、首板前三组。
- 涨停分布采用“题材卡片矩阵”，不是一次性生成所有题材的巨型 HTML 表。每张卡只渲染摘要和前 5 只，点击展开或弹窗查看全部成员。
- 所有时间、金额和百分比统一格式化；原始值保留在 API，前端只负责显示。

### 3.3 板块精选页

默认显示“综合精选”，另有“事件强势”“趋势强势”“持续主线”三个筛选，不把风格标签、近期强势等伪板块混入板块名称。

板块卡内容：板块名称与类型、在线事件强度、本地趋势强度、成交额扩张、成员扩散、连续上榜、代表股、数据来源和更新时间。点击后进入同一个板块详情抽屉，内部包含成员、历史、题材事件和本地证据。

### 3.4 人气热榜页

页面分成两个层次：

1. 个股关注：1 小时人气、24 小时人气、1 小时飙升、24 小时飙升、东方财富热榜。
2. 板块关注：热门概念、热门行业、热门话题。

平台原始名次绝不被本地因子重排。每行并列展示平台字段与本地增强字段；本地增强可筛选但不能改写“平台排名”。跨平台不合成一个总榜，只允许并列对照和代码交集标记。

## 4. 数据合同和来源策略

### 4.1 通用响应信封

每个在线接口必须返回：

```json
{
  "contract_id": "...",
  "dataset": "...",
  "source_id": "...",
  "source_class": "B_PUBLIC_WEB_API",
  "trade_date": "YYYY-MM-DD",
  "source_as_of": null,
  "observed_at_utc": "...",
  "time_semantics": "...",
  "status": "AVAILABLE|PARTIAL|UNAVAILABLE",
  "quality_codes": [],
  "data": {}
}
```

`source_as_of` 缺失时只能使用 `OBSERVED_AT_ONLY`；不能把请求时间冒充来源时间。单个来源失败时返回 `PARTIAL` 和错误码，首页本地能力继续可用。

### 4.2 来源等级与降级顺序

- 同花顺、选股通、东方财富网页公开接口：B 级，可用于个人本地研究；低频、限时、限响应大小、无自动重试风暴。
- 依赖 Cookie 的同花顺市场概况：如果无 Cookie 可正常获取则按 B 级；若必须 Cookie，降为 C 级增强项，不能作为首页唯一来源。
- 龙字诀自有服务、会员鉴权、私有 token：D 级，禁止复用。
- 涨停事实优先同花顺事件池；选股通用于题材和补充事件池；本地规则只作为历史回看或在线失败时的“本地重建口径”，页面必须标注，不得无提示替代。

### 4.3 请求控制

同一页面刷新通过一个聚合服务并发请求，最大工作线程 4；endpoint 内部不再嵌套线程池。每源超时 8–12 秒、响应上限 2 MiB、默认零重试；同一请求共享 session。盘中内存缓存 15–30 秒，收盘历史事件缓存按交易日不可变。用户连续点击刷新时合并相同请求，并取消已经失去页面消费者的请求。

## 5. 模块算法与接口设计

### 5.1 情绪速览

#### 数据来源

- 同花顺涨停池顶部：今日/昨日封板数、炸板数、跌停数和比率。
- 选股通 `pool/detail`：`super_stock`、`limit_up`、`limit_up_broken`、`yesterday_limit_up`、`limit_down`、`new_stock`、`nearly_new`。
- 本地日行情：上涨、下跌、平盘、成交额、MA20/MA60 上方数、创新高数。

#### 聚合规则

1. 市场上涨/下跌/成交额按 A 股证券代码去重，以本地当日行情为准。
2. 涨停/炸板/跌停按同花顺聚合值；成员明细按事件池代码去重。
3. `封板率 = 封板数 / (封板数 + 炸板数)`；分母为 0 时返回 NULL。
4. 昨日涨停今日状态通过证券代码关联；停牌、缺行情、接口未覆盖分别计数，不塞入“未晋级”。
5. 情绪状态只做描述分类，不做概率：
   - `亢奋`：涨停与上涨宽度同时处于近 20 日自身高位；
   - `活跃`：两者至少一项高于近 20 日中位数且封板率不弱；
   - `分化`：涨停活跃但炸板率或下跌宽度同步升高；
   - `低迷`：上涨宽度和涨停数均低于近 20 日中位数；
   - 数据不足：不足 10 个有效历史日。
   阈值采用滚动分位数并版本化，具体值在验证阶段冻结，不在 UI 硬编码。

#### API

- `GET /api/v3/market/overview?trade_date=&mode=LATEST|CLOSE`
- `GET /api/v3/market/emotion/history?days=20`
- `GET /api/v3/market/pools?pool=broken&page=&page_size=`

### 5.2 涨停简图

#### 字段

代码、名称、最新价、当日涨幅、成交额、连板高度、封单金额、流通市值、换手率、首封时间、末封时间、开板次数、涨停类型、题材/原因、来源。

成交额若事件接口不提供，以本地当日行情按代码补齐；没有同日行情则为 NULL，不能拿流通市值替代。

#### 排序

1. 连板高度降序。
2. 同高度末封时间升序，早封优先。
3. 时间相同时封单金额降序。
4. 最后按证券代码稳定排序。

首板单独支持“首封时间、封单金额、成交额、换手率”列排序；用户排序只改变当前视图，不改变基础梯队定义。

#### API

- `GET /api/v3/limit-up/ladder?trade_date=&level=&sort=&page=&page_size=`
- `GET /api/v3/limit-up/stocks/{security_id}` 返回单股事件详情及本地研究增强。

### 5.3 涨停分布

#### 题材归属

以选股通 `plates` 的题材 ID 为分组主键，以 `stocks[].plates[].id` 建立多对多关系。一只股票可出现在多个真实题材中；市场总数按证券去重，题材卡片内允许重复出现。不能根据名称或价格走势猜题材。

同花顺 `reason_type` 用作个股公开题材说明，并用于题材名称同义词映射；不能覆盖选股通原始题材 ID。映射表记录 `source_topic_id → local_sector_id`、匹配方式、置信等级和人工确认状态。

#### 题材统计

- `强势股数`：接口题材成员数。
- `涨停数`：成员中 `up_limit=true` 的证券去重数。
- `最高板`：涨停成员最大板数。
- `成交额`：可获得同日成交额的成员求和，并返回有效成员数。
- `涨停宽度`：涨停数 / 强势股数；只描述该事件池，不冒充板块全体成员宽度。
- `本地板块宽度`：映射成功后，从本地完整板块成员计算，作为独立字段展示。

#### 卡片排序

采用透明字典序，不先做含义不明的总分：涨停数降序 → 最高板降序 → 连板股数降序 → 强势股数降序 → 来源顺序。用户切到“本地增强排序”时，才按映射后的板块精选分数排序，并显示排序依据。

#### API

- `GET /api/v3/limit-up/distribution?trade_date=&include_non_limit=0|1`
- `GET /api/v3/limit-up/topics/{source_topic_id}?page=&page_size=`

主响应只含题材摘要和每题材前 5 名；完整成员按题材单独分页，避免 DOM 和响应膨胀。

### 5.4 最强题材

“最强题材”不是简单复制涨停分布。它是在事件题材上叠加本地持续性后形成的研究排序。

#### 基础资格

题材至少满足一个条件：涨停数 ≥ 2；或有二板及以上成员；或强势股数 ≥ 4 且本地板块上涨宽度有效。ST 题材和无法映射到 A 股的成员排除；个股可重复归属，但题材内按代码去重。

#### 透明评分

仅用于题材研究排序，不表达概率：

```text
topic_research_score =
  0.30 × event_strength_pct
+ 0.25 × local_rps20_pct
+ 0.20 × continuity_pct
+ 0.15 × breadth_pct
+ 0.10 × amount_expansion_pct
```

- `event_strength_pct`：由涨停数、最高板、连板数形成的同日题材百分位；原始三项同时返回。
- `local_rps20_pct`：映射本地板块的 20 日相对强度百分位。
- `continuity_pct`：近 5/10 日进入事件题材前列或本地主线的频次百分位。
- `breadth_pct`：本地板块有效成员上涨宽度百分位。
- `amount_expansion_pct`：板块共同成员成交额相对前 20 日均值的百分位。

任一项缺失不补 0。有效权重重新归一化，但至少需要事件强度以及另外两项本地证据；否则标为“事件观察”，不进入综合精选。权重、最低覆盖和字段定义进入版本化合同，发布前使用历史样本做稳定性审计，不以未来收益调参。

#### 代表股

题材内先按是否涨停、板位、首次封板、成交额、RPS20 排序。代表股必须来自该题材实际成员；最多 3 只，且展示“事件龙头”“趋势代表”“成交活跃”角色，角色可由同一只股票兼任，但不重复显示。

### 5.5 人气热榜

#### 榜单集合

- 同花顺：`HOUR_NORMAL`、`DAY_NORMAL`、`HOUR_SKYROCKET`、`DAY_SKYROCKET`。
- 同花顺板块：`PLATE_CONCEPT`、`PLATE_INDUSTRY`。
- 同花顺话题：`TOPIC`。
- 东方财富：保留现有 A 股热榜作为独立来源。

#### 处理规则

1. `platform_rank` 永远采用来源 `order`，不得按本地涨幅重排。
2. `rank_change` 只表示来源字段，不伪装成本项目跨时点计算。
3. 证券映射仅接受明确市场代码；SH/SZ/BJ A 股范围外标为 `OUT_OF_SCOPE`。
4. 来源的涨幅、热度、标签原样归于 `source_fields`；最新价、成交额、MA、RPS、五类结构归于 `local_enrichment`。
5. 热榜请求级直取，不保存原始载荷、行、批次或历史快照；仅可使用 15–30 秒进程内缓存和请求去重。
6. 页面允许“只看同时进入两平台”“只看进入本地优先研究”筛选，但不生成综合名次。

#### API

- 扩展 `GET /api/hot-rankings` 或新增 `/api/v3/hot-rankings`，参数包括 `source`、`list_type`、`page`、`page_size`。
- `source=ALL` 时返回来源独立的 `source_views`，失败来源独立标错。
- 板块榜与个股榜使用不同 DTO，不复用证券字段硬塞。

### 5.6 板块精选

板块精选使用在线事件与本地研究合并，是本项目最需要形成特色的模块。

#### 候选集合

候选取并集：当日最强题材、同花顺热门概念/行业、本地主线 `NEW/SUSTAINED/REACCELERATING`、本地板块 RPS20 前 15%、成交额扩张前 15%。普通“近期强势、昨日首板、昨日连板”等股票池标签不得当成板块。

#### 映射门

在线板块未映射本地板块时，只进入“事件强势”，可展示来源成员，不参与本地综合评分。映射需要源 ID 优先、规范名称其次、人工覆盖最后；模糊名称不得自动高置信合并。

#### 综合精选分

```text
sector_select_score =
  0.25 × online_event_pct
+ 0.20 × local_rps20_pct
+ 0.15 × local_rps5_pct
+ 0.15 × continuity_pct
+ 0.10 × breadth_pct
+ 0.10 × amount_expansion_pct
+ 0.05 × member_retention_pct
```

高位收缩、成员快速流失、金额覆盖不足作为明确风险标签，不直接偷偷扣分。综合精选至少要求在线事件或本地主线一项成立，并有 4 项有效分量；否则进入对应单源标签页。页面同时展示分量条形，不只显示总分。

#### 去重与层级

行业父子板块同时入选时保留二者，但首页只展示得分更高且证据更具体的一层；详情显示父子关系。概念与行业不互相去重。来源题材与本地概念同义映射后合成一张卡，但保留两个 source reference。

## 6. 数据库改造

### 6.1 原则

1. 在线事件数据按“发生事件的实体”存储，不每日复制全市场。
2. 热榜严格不落盘。
3. 原始响应不塞入 DuckDB 大字段；允许保存的非热榜来源采用内容寻址压缩对象，DuckDB 只记哈希与引用。
4. 本地全市场历史表不为这些页面重复计算；融合查询按事件股票集合批量读取本地字段。
5. 任何新表都有合同版本、来源时间、观察时间、质量码和唯一键。

### 6.2 建议新增/调整表

| 表 | 主键 | 用途与规模 |
|---|---|---|
| `online_dataset_contracts` | `contract_id` | 来源 URL 模板、参数、字段映射、能力、版本、失效策略 |
| `online_fetch_runs`（扩展现有） | `fetch_id` | 请求元数据、HTTP 状态、耗时、字节数、哈希；不存热榜正文 |
| `market_emotion_daily` | `trade_date, basis` | 每日一行；在线观测与本地重建分 basis |
| `market_pool_entries` | `trade_date, pool_type, security_id` | 只存强势、涨停、炸板、跌停等事件股票，通常数十到数百行/日 |
| `limit_event_daily` | `trade_date, security_id` | 封板时间、板位、开板、封单、原因、状态和来源 |
| `topic_event_daily` | `trade_date, source_id, source_topic_id` | 当日活跃题材摘要 |
| `topic_event_members` | `trade_date, source_id, source_topic_id, security_id` | 当日题材事件成员，多对多但仅活跃集合 |
| `source_sector_map` | `source_id, source_sector_id, mapping_version` | 在线题材到本地板块映射、证据和人工覆盖 |
| `sector_selection_daily` | `trade_date, sector_id, contract_id` | 仅保存精选候选及分量，建议每日不超过 300 行 |

不新增 `hot_rank_entries` 的请求级数据。现有在线热榜历史批次能力停止作为新页面依赖；若已有个人研究文件，保留只读，不迁移为生产历史。

### 6.3 与现有表的读取关系

- `stock_technical_daily`、`stock_strength_daily`、`stock_high_daily`：只对事件成员或页面请求的股票批量 join；新功能不触发全市场重算。
- `sector_cycle_daily`、`mainline_daily`：为最强题材和板块精选提供本地增强。
- `sector_member_state_daily`：板块详情分页读取，不复制到事件表。
- `limit_ladder_daily`：保留为本地重建历史，不再作为当日涨停简图唯一来源。
- `market_cycle_daily`：保留历史市场研究；当日在线概况通过 `basis=ONLINE_OBSERVED` 并列显示。

### 6.4 数据膨胀临时门

在全面治理前先执行四个非破坏性门：

1. 新切片若输入哈希与已有成功切片相同，必须复用，不得再插全量行。
2. 页面刷新绝不触发物化任务。
3. 在线事件只物化事件集合，热榜零持久化。
4. 每个构建任务先输出预计新增行数和字节数；超过合同预算则拒绝提交。

历史重复切片的识别、引用图、压缩和垃圾回收另建 `STORAGE-EXPLOSION-AUDIT-01`，必须先做只读清单和可恢复计划，不能直接删除。

## 8. 必须建立的验收样例

1. 同花顺顶部封板 40、炸板 18 时，封板率必须为 `40 / 58`，不能使用 `18 / 40`。
2. 同一股票属于 3 个题材时，三个题材均显示该股，市场涨停总数只计 1。
3. `4天3板` 的板位为 3；`首板` 为 1；无法解析不能静默当首板，应标质量码。
4. 同高度股票末封时间早者排前；时间缺失者排在有效时间之后。
5. 在线题材无法映射本地板块时，仍可显示事件事实，但 RPS、连续性和综合精选为不可用。
6. 热榜平台第 1 名即使本地涨幅最低，仍保持平台第 1；本地筛选不改名次。
7. 在线接口超时后，首页市场本地数据仍出现；在线卡片显示来源暂不可用和上次成功时间。
8. 页面打开涨停分布时，初始响应不包含每个题材全部成员；展开一个题材只请求该题材成员。
9. 当日事件接口与本地行情交易日不一致时禁止融合，返回 `TRADE_DATE_MISMATCH`。
10. 每日新增数据预算以事件规模为主，不能因为新增这些页面再产生一份全市场 × 板块 × 窗口明细。

## 10. 风险与决策

1. 网页公开接口可能变更：所有字段解析必须 fail closed，不能把空列表当真实 0。
2. 题材定义跨来源不同：必须保留 source topic ID 和本地 sector ID 两套身份，不做不可逆合并。
3. 盘中值会变化：首页显示更新时间；收盘后才能形成稳定的每日事件快照。
4. 原因字段的语义：同花顺 `reason_type` 可显示为“来源题材/原因说明”，但不得宣称是交易所官方涨停原因。
5. 本地历史重建仍有价值：它用于长历史、MA/RPS 和接口缺历史时的研究，不应被删除；但当日事实优先在线事件池。
6. 数据库已膨胀：新功能必须稀疏化，旧数据清理另审计，不能在功能升级中顺带破坏历史引用。

## 11. 最终完成定义

目标版本只有同时满足以下条件才算完成：

- 用户从首页两次点击内能到达最强题材、涨停分布、涨停简图、情绪速览、人气热榜和板块精选。
- 当日涨停相关事实来自已验证在线事件池，并清楚显示来源与时间；本地重建不再无提示顶替。
- 最强题材和板块精选真正融合在线事件与本地 RPS、连续性、宽度、成交额、留存数据，所有分量可解释。
- 个股页面区分事件题材、强势关联板块和普通属性板块，不再用“近期强势”等标签占据所属板块。
- 所有列表由服务端分页或按需请求，浏览器不接收全量数据库数据。
- 热榜零持久化；新增每日持久化规模与事件数量同阶，不与全市场证券数 × 板块数 × 窗口数相乘。
- 在线失败不阻塞本地主流程；来源漂移、日期错配和缺失均有明确状态。
- 阶段 R0–R8 均有独立合同、证据、验收结果和下一阶段记录，最终经过源码、数据库、接口、页面和性能联合审计。

## 12. 本次方案审计结果

本方案已按功能依赖重新排序：先来源和合同，再市场事件，再涨停明细，再题材聚合，再热榜和板块精选，最后首页融合；不存在先做页面再补数据基础的倒置。方案同时覆盖了数据源、字段、算法、接口、数据库、UI、降级、性能、测试和发布门。

仍需在实际开发 R0 阶段冻结的项目只有三类：各公开接口的最终字段样例与使用条款状态、情绪分类滚动分位阈值、板块精选权重的历史稳定性。它们不能靠文档猜定，但不会改变总体架构。

结论：这些功能技术上可以实现，并且比继续依赖全市场日线重建更接近用户需要。实施时应把本文作为目标版本主计划，原 M7–M15 文档作为底层数据和历史能力参考，而不是两份方案并行执行。
