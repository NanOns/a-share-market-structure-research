- Design state: `PARTIAL / NOT_EXECUTABLE`
- Inventory date: 2026-10-16 (Asia/Shanghai)
- Database: existing `127.0.0.1:5432/market_research`; catalog queries ran in read-only transactions
- Production runtime at inventory: `NOT_RUNNING`; ports 28765 and 28766 had no listener
- Read connection: V4 reader role, then explicit V4 DSN, then the existing `WORKBENCH_PG_DSN`; write connections still require explicit `V4_NATIVE_PG_DSN`

This is a field-level migration design, not evidence that data was migrated or accepted. It does not authorize DDL, PG writes, Head movement, service startup, source-file cleanup, or production cutover.

The V4 read connector now reuses the project's existing Workbench DSN only through the `read_only=True` connection path when no V4-specific DSN is configured. The writer connector remains fail-closed and still requires its explicit V4 DSN. No DSN value was added to code or documentation.

Neither file was modified. Their referenced JSON/GZ payloads were not decoded or displayed; only declared path, size and SHA metadata were compared with the local bytes. Source roots remain read-only. The earlier WP-0 statement that no current production process was running remains true; the earlier statement that there was no local Head file is corrected by this inventory.

The Head descriptors and current read contracts were subsequently SHA-256 checked without decoding business payloads. All referenced local paths exist. `V4_DATA_ACCEPTED_HEAD` has 39 reference occurrences / 30 unique files; 38 occurrences match their recorded SHA and one (`stage_head`) does not match its recorded size or SHA. `V4_OPERATIONAL_RESEARCH_HEAD` has 136 occurrences / 121 unique files; 84 occurrences match and 52 do not (8 source-code references and 44 docs/evidence references; 49 unique files). This makes the operational file Head unsuitable as a current integrity-verified producer identity.

The tracked `V4_CURRENT_ACCEPTED_READ_CONTRACT_V1` has `source_discovery=false`, `fallback=NONE`, and accepted date 2026-09-30, but binds 390 files: 27 under `data/` and 363 under `reports/`. The report references include 117 cohort rows, 117 ledger rows, 117 observations, 5 outcomes, and 7 additional report-source bindings. All report references match their declared SHA; two of the 27 data references (`sources.events` and `sources.states`) do not. `CurrentAcceptedV4Reader` verifies and reads these bindings for corresponding modules, so the report dependency is part of the current code path even though the runtime service is stopped.

The tracked `V4_PRODUCTION_RUNTIME_AUTHORITY_V1` records a read-only UI, no TDX writes, no trading actions, `V4_ACCEPTED_RESEARCH_READONLY`, and a binding to the current read contract. Its six local references match their recorded SHA. This is configured authority, not proof of a running service or current accepted PG Head.

The eight owner-head JSONs bound by the read contract include embedded evidence references. `V4_12_ACCEPTED_HEAD_V1` alone contains 3,589 such references, 3,477 under `reports/`. These nested references are not all direct source bindings: `CurrentAcceptedV4Reader` follows selected contract, permission, and row bindings. The migration must trace each value actually consumed instead of either importing the complete evidence graph or assuming all embedded references are irrelevant.

The current `V4_RESEARCH_SNAPSHOT_AUTHORITY_V1` manifest is internally hash-bound but its `database` reference is a 440 MB `research.sqlite` file. The current `ProductionV4ResearchReader` requires a PostgreSQL JSON descriptor whose engine, accepted trade date (`T0`), and `release_id` match the manifest; it explicitly rejects any other storage engine and rejects a mismatched context. A populated PG research snapshot exists in `v4_research_e30350bf444bbb9980cf3e2c` with 6,337 objects, 50,162 members, and 12,106 aliases; its metadata says 2026-09-30, `VALIDATION_ONGOING`, `QUALITY_DEGRADED`, and `FP02_INDEXED_EXISTING_REAL_OUTPUTS`. Its release ID differs from the current SQLite authority's release ID. The inventory found no authority-bound PG descriptor for this candidate. Other PG research namespaces are empty or hold separate bar-series tables. None is currently bound by the snapshot authority. Do not delete the SQLite file or repoint the authority until a compatible PG descriptor, matching release context, and rollback path are verified.

## Design constraints and write gate

1. Reuse existing `v4` publication/source/history structures and existing immutable Owner schemas where their owner/token and content identity are verified. Do not create a generic duplicate registry before the missing publication-to-owner relationship is demonstrated.
2. If an association table is needed, first prove the minimal key and FK design against the existing publication keys, domain names, Owner schema/token/T0, immutable digest, producer/input digest, quality, and clocks. A schema name string cannot provide a normal cross-schema FK to dynamically hashed Owner tables; the loader must verify the referenced immutable version and database identity in the same accepted-read boundary.
3. `source_packages` and `publication_consumed_sources` are currently empty; define how package facts become a revision and how a publication records consumed source revisions before writing any rows.
4. Draft executable SQL must include unique/FK constraints, indexes, roles, parameters, bounded row counts, readonly preflight, idempotent rerun, conflicting-SHA rejection, transaction boundary, before/after checks, and rollback semantics. It must not move a Head during import.
5. A write request must state the exact schema/tables, expected rows, whether writes are append-only, the affected data and consumers, transaction/rollback plan, privilege source, and post-write cleanup responsibility. All writes use the existing `market_research` instance; no new DB or port.
6. Keep `M14` approved-source contracts and its non-persistence hotlist exception. No change to the TDX source root or to existing accepted data during this design stage.
