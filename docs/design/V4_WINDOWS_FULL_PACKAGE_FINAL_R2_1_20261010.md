## 2. 现有基础与最小必要改造

源码核对确认：

1. `run_workbench_service.py`的V4入口为 `core_product_server_r1.py::serve_v4`，当前网页为 `http://127.0.0.1:28765/v4`。
2. 已有服务/日更读API及 `DailyJobs.status()/settings()/job()/events()`，继续复用，不新建另一套调度系统。
3. `DailyJobs`使用SQLite/WAL；工作线程是daemon，`close()`只等待2秒，尚不能直接承诺安全退出。
4. 已有PowerShell托盘依赖 `E:\\python\\python.exe`或PATH，部分启停菜单禁用；最终产品必须由打包程序启动，不能仅把旧脚本包装成快捷方式或打开禁用按钮。

7. 维护停机若直接使用现有用户取消语义，会阻止后续自动补跑；必须区分维护中断和用户主动取消。

## 3. 产品结构与两个内部生命周期

```text
大A交易系统安装程序.exe
  └─ 完整程序目录：主EXE、内置Python、依赖、网页、合同资源、版本清单
      └─ 大A交易.exe（桌面快捷方式／可选用户登录自启）
          ├─ 托盘/UI消息循环：持续存在，直到退出应用
          │   └─ 启动引擎／安全停止／安全重启／日更开关／网页／日志
          └─ EngineController：应用内部状态机
              ├─ 现有V4本机HTTP工作台：127.0.0.1:28765/v4
              └─ 现有DailyJobs及SQLite、原发布与回读事务

G盘持久工作区
  └─ Head、冻结原件、运行数据库、日志、用户设置和版本化证据

TDX及配置的源目录
  └─ 只读输入
```

首版采用同一应用进程：主线程承载轻量托盘/消息循环；内部EngineController管理HTTP服务线程和DailyJobs，不另建进程、服务或调度系统。UI只提交短小控制请求，耗时工作不阻塞托盘。具体托盘组件在S0核对Windows兼容性后锁定版本。

托盘生命周期与引擎生命周期分别管理：引擎停止后托盘仍可接受启动请求；退出应用必须先安全停引擎，再退出托盘。整个EXE崩溃时两者一起消失，用户可再次双击启动，首版不承诺托盘在进程死亡后仍存在。

不新增独立Supervisor、Windows Service、WPF控制中心或常驻管理IPC服务。现有数据来源、模型、Owner、Writer和正式能力准入继续由原合同控制。

### 用户操作与观察窗口

- 双击主EXE后启动托盘，先校验工作区、版本与端口；默认请求启动引擎，确认RUNNING后再打开V4网页。
- 重复点击快捷方式时定位已核验的应用，不启动第二套线程；若当前引擎STOPPED，只打开托盘状态提示，不隐式撤销用户手动停止意图。
- 托盘提供“启动引擎”“安全停止引擎”“安全重启引擎”；安全停止只停引擎，托盘继续存在。首版“安全重启”只重启当前包版本的引擎，升级由安装流程管理。
- 关闭网页不改变引擎或日更设置；“退出大A应用”安全停止引擎后关闭整个应用。
- 启动失败时托盘保留FAILED状态、原因与重试入口，即使网页不可用仍能操作。引擎停止后显示上次记录和观测时间，不显示实时绿色状态。
- “登录Windows后自动启动”是可选设置，默认随应用启动请求启动引擎；用户日更暂停设置保持原值。关机、休眠、未登录或引擎停止时不保证采集。
- 自启设置和运行首页醒目显示 `CAPTURE_REQUIRES_APP_RUNNING`：“真实首次观测需要电脑可用、用户已登录、应用及引擎运行，并满足来源与调度条件。”提示还应结合日更是否暂停；不能把托盘存在当作正在采集。
- 下一实际交易日及采集窗口按原交易日历提醒，退出/停止时说明可能错过首次观测。首版不自动阻止休眠或引入唤醒计划任务。
- 错过本机既定首次观测窗口时显示 `MISSED_REAL_FIRST_CAPTURE`并记录目标、窗口、可证明的离线事实/观察缺口及实际恢复时间。没有足够证据时标记“无法确认首次观测”，不能声称全局来源首获已丢失或捏造停机起止。
- 恢复后由原缺口计划补日更；补采时间仍是实际观测时间，不补造历史first_available。归档回放也不能算真实新日首获。

## 4. 打包、安装与路径合同

### 4.1 交付方式

采用PyInstaller目录模式整体打包，再制作一个Windows x64安装程序。包内含Python运行时、实际V4运行依赖、静态网页资源、必要配置模板与验证资源。依赖版本和构建工具版本固定在构建清单中。

不能只打包启动器，再从系统PATH寻找Python或要求用户安装pip依赖。动态导入、数值库、本机扩展、`scripts`运行依赖与数据文件需要按真实调用链显式纳入并验证。已接受算法需要核对源码原字节时，保留对应原件及清单，不能仅用打包后的字节码冒充原源码SHA。

安装交付包含：

- `大A交易系统安装程序.exe`。
- 桌面/开始菜单“大A交易”快捷方式，指向主EXE。
- 完整程序目录、版本清单、使用说明及卸载入口。
- 包版本、构建ID、源码提交、资源摘要和兼容性清单。

安装器只负责文件部署、快捷方式和用户选择的登录自启。应用以普通当前用户运行；常规启动和日更不要求管理员PowerShell。无需引入自动更新服务，首版采用用户主动安装新版。

### 4.2 程序、工作区和临时目录

| 类型 | 规则 |
|---|---|
| 程序资源根 | G盘版本化安装目录，例如 `G:/codex work/大A交易_安装版/releases/<版本>`；用于EXE、库和只读资源 |
| 持久工作区 | G盘固定目录，保存Head、原件、任务数据库、日志和设置；路径与包版本分别记录 |
| 当前生产工作区 | 初始只盘点和验证现有 `G:/codex work/大A交易`，不在设计或构建阶段自动搬迁、替换或接管 |
| 工程构建/缓存/临时 | `G:/codex_tmp`；测试临时目录 `G:/codex_tmp/test_temp`；子命令设置TMP、TEMP、TMPDIR |
| TDX及配置源目录 | `D:/new_tdx`及所有已配置源根永远只读 |
| 卸载 | 默认保留研究数据、冻结原件、Head和日志；删除用户数据需要用户明确选择和授权 |

以上安装路径是设计建议，不是本次新建或迁移生产目录的指令。

资源查找必须显式区分打包资源根和持久工作区，不能继续把 `Path(__file__).parent`、当前工作目录或单文件解压目录当作数据根。持久原件的相对引用必须仍可在选定工作区解析；包内固定合同资源采用经过验证的路径映射，不能为迁移方便改写已接受原件或取消SHA检查。

打包器只收集已识别运行依赖及其有界引用闭包，不整仓复制庞大证据、测试夹具和行情数据。现有研究数据仍由固定工作区提供，未验证数据根时阻止启动任务。

正式产物在TDX之外原子写入。程序运行不修改安装资源和Git源码；确需读源码/合同原件时只读。没有G盘、磁盘未挂载或工作区不可写时明确报错，不静默改用C盘缓存或另起空工作区。

### 4.3 冻结运行链与子任务合同

S0输出 `FROZEN_TASK_DISPATCH_V1`及实际可达调用图，覆盖启动、DailyJobs、来源、derive、CAS/readback/recover和用户允许的手动操作。扫描 `sys.executable`、`subprocess`、`multiprocessing`、动态导入、路径与源码原字节依赖，并结合运行跟踪逐条标记“可达／不可达及证据／待核实”。待核实的必需路径不能计为打包闭环。

- 优先将可达子脚本适配为受控模块内调用；需要隔离进程时，使用同一EXE固定子命令白名单，例如 `--task=<已登记任务>`，只执行注册处理器。
- 子任务分派在托盘初始化、自动启动HTTP与调度之前完成，防止递归拉起UI或第二个引擎。冻结模式禁止原样执行 `[sys.executable, '-X', 'utf8', script]`、`-m`、任意路径或任意代码；不得回退系统PATH/Python。
- 子任务限定工作区、参数、超时、输出协议、退出码和权限；不另建调度器或写入Owner。应用拥有工作区锁与发布权，现有需要写入的脚本优先模块内调用；不得凭 `--task`参数绕过独占锁或正式合同。
- 若实际使用multiprocessing，按PyInstaller合同在相关导入/GUI启动前完成 `freeze_support()`及子进程分派；不使用则记录不可达证据，不为此新增并行框架。
- 受控子进程TMP/TEMP/TMPDIR均落G盘。外部系统程序/浏览器的启动如受打包DLL搜索环境影响，应针对子进程隔离处理，不在并发线程中无保护修改全局搜索路径。
- 开发入口保留原受支持执行方式；新增适配不改变已接受算法含义和权限，运行原件SHA依赖必须可复核。

资源manifest白名单覆盖动态模块、源码原件、合同、脚本子任务、本机DLL/PYD、网页及实际使用的字体等。缺资源给明确错误，不静默跳过。

运行状态读回 `APP_RESOURCE_ROOT`、`WORKSPACE_ROOT`、`BUILD_RELEASE_ID`、`SOURCE_SHA`、`RESOURCE_MANIFEST_SHA`、`WORKSPACE_SCHEMA_VERSION`及实例ID。这些是执行身份事实，不是新的正式业务准入；缺少字段时不能伪造默认版本。

STOPPED时只启用启动；RUNNING时启用安全停止和安全重启；STARTING、QUIESCING、WAITING_SAFE_BOUNDARY、STOPPING期间显示操作ID、阶段和等待进度，重复动作不再发起第二次操作。FAILED状态先确认资源回收与旧线程退出，满足条件后才允许重试启动。

引擎停止时“打开网页”不可伪称可用；显示停止原因和启动入口。日更开关的读取/修改由同一版本化设置适配器完成；引擎停止时只允许不触发任务的原子设置操作，与启动/停止操作串行，不另起worker。状态快照注明观测时间。

UI标签区分“停止引擎”和“退出应用”；首版不提供强制发布或普通菜单强杀。最近错误用中文解释并保留可复制错误码；不增加完整桌面管理台。

### 5.2 保留四类事实展示

原稿对运行事实的分层继续保留，集中在现有网页及简短托盘状态中：

1. **应用/引擎运行**：托盘应用是否存在与引擎状态分别显示；当前实例ID、PID、包版本、运行模式、端口、最近状态观测时间。端口返回200但身份或版本不符，显示 `WRONG_ENGINE_AT_PORT`。
2. **自动日更**：开启/用户暂停、下一次触发、当前任务、阶段、重试时间和最后错误。应用停止与暂停日更分别说明。
3. **数据状态**：运营Research Head与strict Data Head各自接受日期、真实源截止和上次成功/失败；`WAIT_TDX`、`WAIT_BAOSTOCK_DAILY`、`WAIT_DATED_IDENTITY_AUTHORITY`、`SOURCE_GAPS`分别解释。
4. **正式准入**：Research Read、State、D2、Cohort、FEP分别展示实际授权与来源，工程候选不显示为正式上线。

HTTP200不等于日更成功、数据最新或能力已准入。离线时显示“上次记录＋观测时间／当前不可确认”，不把缓存继续显示为实时绿色状态。

应用活性检查建议每5秒进行一次，仅访问轻量本机状态；连续3次失败标记“状态不可确认”，不据此自动杀进程。启动时验证身份、版本、调度线程和数据根；活性与数据就绪分别判定。日期新鲜度按已接受交易日历及盘后可用时间判断，不按自然日强行要求更新。

完整诊断、头历史检索和高级提醒属于后续增强。首版只提供最近错误、日志目录和脱敏小型诊断包，不自动上传凭证或大规模原始行情。

## 6. 引擎启停重启、安全退出与发布事务

### 6.1 引擎状态机及操作语义

`STOPPED / STARTING / RUNNING / QUIESCING / WAITING_SAFE_BOUNDARY / STOPPING / FAILED`。

正常转换：STOPPED→STARTING→RUNNING；RUNNING→QUIESCING→WAITING_SAFE_BOUNDARY（仅忙任务需要）→STOPPING→STOPPED。初始化或回收失败进入FAILED，保留原因；未证实旧资源释放时禁止再次启动。

| 操作 | 行为 |
|---|---|
| 启动引擎 | 应用已取得工作区生命周期锁；核验旧资源已释放、包/工作区/端口，执行合法恢复，再创建全新的server/jobs和线程 |
| 安全停止引擎 | 关闭新任务准入、停止新tick，等待活动工作至事务安全边界及必要HTTP回读，关闭server与连接，确认线程回收；托盘继续运行 |
| 安全重启引擎 | 同一操作ID下完成安全停止；只有STOPPED并确认旧线程退出后才启动新对象；停止失败时不得抢先启动 |
| 暂停／恢复自动日更 | 沿用版本化既有设置与日历计划，保留原发布门；暂停不等于停引擎或用户取消 |
| 用户取消任务 | 保持既有取消保护；应用或引擎重启不自动恢复用户取消任务 |
| 退出应用 | 提交安全停止；已经STOPPED则直接退出托盘。忙任务收尾时UI保留响应，停止完成后才退出 |
| 再次启动应用 | 重新创建运行对象，恢复原用户日更开关，按检查点恢复合法维护中断，不改变正式权限 |

引擎停止不把 `auto_enabled`强制改False；引擎再次启动恢复用户原值。用户暂停、手动STOP_ENGINE、维护中断和退出应用分别记录。应用存活期间手动停止保持STOPPED，不由心跳或重复快捷方式自动重启。

当前 `serve_v4()`需提取可管理的启动、等待、停止和资源所有权接口；不能仅在daemon线程中反复调用旧函数。再次启动必须重建已关闭的HTTPServer、DailyJobs、stop Event及线程，不复用旧对象；已接受算法、来源和发布合同不变。

维护中断与用户取消分别记录，例如版本化 `MAINTENANCE_INTERRUPTED`原因和可恢复检查点；不能直接留下用户 `CANCELLED`状态，也不能删除用户取消保护。若实际发布已完成，按真实结果记录，不能把已提交日期标成中断。

停止顺序必须可取证：

1. 由EngineController串行处理带操作ID的启动/停止/重启；所有入队和tick入口在同一准入边界检查QUIESCING，拒绝新写任务。
2. 停止新tick，等待当前不可变捕获和协作安全边界；发布中的HTTP读服务保持可用，完成回读及事务收尾。
3. 确认无活动事务与写入者后，由其他线程调用HTTP shutdown；关闭server、任务/请求线程及数据库连接，验证WAL一致性。不能在HTTP循环中同步等待自身停止。
4. 确认旧线程、端口与资源回收，记录STOPPED。保持应用生命周期锁，托盘仍可安全读取快照；退出整个应用后才释放该锁。

120秒仅为提示阈值：显示“尚未到安全边界”，继续等待、不自动强杀、不伪称停止。取消停止请求只能在资源最终关闭前恢复准入，并保留原日更开关；已开始最终关闭则等待STOPPED后重新启动，不能复活已关闭对象。WAITING期间可取消后续重启/退出意图，不能另发并行重启。来源请求仍有超时和有界重试。

FAILED状态必须说明是启动失败还是停止失败，以及尚未回收的资源；不得将“线程join超时”当STOPPED。

### 6.2 发布完成的边界

- `PREPARED`：已准备事务，尚未最终提交。
- `CAS_COMPLETE_READBACK_PENDING`：Head已CAS写入，HTTP回读尚未结束。
- `COMMITTED`：发布验证完成，最终提交已记录。

“保护已发布Head”指保护**最终COMMITTED的合法Head**。管理器或安装器不能把它覆盖为旧快照。未提交事务仍由既有 `promote()/recover()`及CAS保护处理；不得改变原回读失败恢复前驱的合同。

只允许关闭新写入入口，不在回读中途关闭读服务。安全停止、重启和退出应用都遵守这一边界；最终提交后不回退已发布日期，发布期间收到维护请求按真实事务结果收尾。

### 6.3 系统关机与意外结束

本方案是用户桌面应用，不承诺Windows关机时无限等待。区分主动安全退出、用户注销/系统关机通知、进程崩溃和断电。

收到系统会话结束通知后尽快停止新任务并持久化检查点；若Windows强制结束或断电，记录可证明的中断状态，下一次启动按原恢复协议核验。只有完整收尾和确认进程退出后才记录“安全退出完成”。不得删除SQLite的WAL来假装已刷盘；连接关闭与一致性备份需按数据库约束执行。
